🏗️ Architecture Overview

Monorepo Structure

contract/ — Shared HTTP contract (route table, DTOs, canonical signing + regime rules); zero runtime dependencies, vendored into the frontend by bun run sync-contract

frontend/ — Buildless static SPA (HTML + Alpine.js + CSS); no build step required

backend/ — Bun processes sharing one source tree: the api (HTTP + optional static serving when STATIC_DIR is set), one worker per queue lane, and the independent analytics-producer, which holds no database credential at all

scripts/ — the smoke/stage stack driver, preview server, goldens capture, evals and checks

Frontend Stack

  • Alpine.js (v3.14.9) — Reactive SPA framework
  • Chart.js (v4.5.1) — Time-series charting
  • p5.js (v1.11.2) — Generative graphics & animations
  • HTML5/CSS3 — Zero transpilation

Backend Stack

  • Bun (≥1.2) — JavaScript runtime & server
  • Postgres — Persistent state & job queue
  • TypeScript (^5.9.3) — Type safety
Design Philosophy: minimal dependencies and no frontend build step; one route table shared by both sides; a Postgres-backed task queue for background work; and fail-closed configuration throughout — an unset or unrecognized value refuses to start rather than guessing (RM_ENV, WORKER_LANE, ANALYTICS_SOURCE, BASE_RPC_SOURCE, PROJECTS_SOURCE in prod).

Comments API

Public comments. Location: backend/src/api/routes/comments.ts. GET and POST share the single path /api/comments; the thread is selected by the ?page= query slug, not a path parameter.

Endpoint Method Purpose

Analytics API — a WRITE boundary, not a read API

Location: backend/src/api/routes/analytics.ts. This is the analytics-provider ingestion surface: updater processes submit computed outputs here instead of writing SQL, and the API process is the only runtime component that imports the analytics store writers. Public read feeds live under /api/dashboards/*.

Requires: the ANALYTICS_TOKEN bearer (analytics-provider role, constant-time compared). ADMIN_TOKEN and member bearers are never substitutes. Unauthenticated → 401; wrong credential → 403.

Endpoint Method Purpose
/api/analytics/readiness GET Producer boot probe — authenticates the credential only; reads and mutates nothing
/api/analytics/raw-history GET / POST The only data route accepting GET. POST batch-upserts on (date, indicator).
/api/analytics/raw-history/seed POST Cold-DB gap fill (existing rows win) — EDGAR seed ingestion
/api/analytics/regime-snapshots POST Snapshot batch upsert on (date). GET returns 405.
/api/analytics/research-signals POST Signal batch upsert on (signal_key, date). GET returns 405.
/api/analytics/telemetry POST One run's structured telemetry (stages, warnings, artifacts, outcome). Non-fatal: a failed telemetry submission never blocks the canonical writes.
/api/analytics/research-eligibility POST Retired control-plane path. Authenticated callers get 409 and no schedule/job mutation — retained so old clients fail closed.
Every mutation validates the entire payload before opening a transaction, runs inside one transaction, and is idempotent on its natural key. There is no generic SQL-over-HTTP endpoint.

Analytics Producer Service

Location: backend/src/producer/index.ts

The independent analytics/research producer (decision D25, issue #361). It runs as its own container (analytics-producer in docker-compose.yml) with no DATABASE_URL, no queue access and no ADMIN_TOKEN: it computes on its own side and can persist only by submitting through /api/analytics/* under its secret-file-mounted provider bearer.

⚡ Worker Queue & Background Jobs

Worker Architecture

Location: backend/src/worker/

Job Lanes

A lane is not a priority or a concurrency setting. It is a pair of SQL LIKE pattern lists (include / exclude) applied inside the FOR UPDATE SKIP LOCKED claim query — it only narrows WHICH pending kinds a worker may claim. Production runs one container per lane.

  • swarm — RESERVED interactive lane: claims only swarm.%. No other lane may take those, so session lifecycle work is always immediately claimable.
  • analytics — everything EXCEPT swarm.% and research.%. In practice that is the vault / wallet / buybacks / projects pipelines — it excludes research.
  • research — compatibility lane for legacy research.% rows. Since D25 the independent producer owns supported research execution and nothing can enqueue new rows here.
  • generic — dev/tooling convenience: everything EXCEPT the reserved swarm.% kinds. Not part of the compose topology.

WORKER_LANE is REQUIRED. An empty or unknown value throws in resolveLane() at startup — there is deliberately no default, because a misconfigured worker silently claiming everything would eat the reserved swarm capacity.

Core Modules

  • index.ts — process entry: resolves the lane, starts the runtime, handles SIGINT/SIGTERM
  • runtime.ts — composes the three loops behind one start/stop handle; owns the bounded shutdown contract (release the in-flight job back to pending rather than orphan it)
  • loop.ts — the lane-filtered claim/drain loop and the ownership-guarded terminal writes
  • scheduler.ts — ticks job_schedules into jobs
  • reaper.ts — recovers jobs whose lease expired
  • lanes.ts — the include/exclude pattern table and resolveLane()

Job Handlers

The worker is an updater, not a writer for analytics: it never writes analytics SQL, it submits through the authenticated /api/analytics/* boundary (ANALYTICS_API_URL + ANALYTICS_TOKEN). Its own DB connection is scoped to queue lifecycle plus the non-analytics samplers.

Job Lifecycle

Status is a CHECK-constrained enum in 0003_task_queue.sql: pending → running → succeeded | failed | dead. Those five are the whole vocabulary.

  • Enqueue — a row in jobs with a kind and payload. An optional dedupe_key (unique partial index) means a schedule slot enqueues at most once even with several schedulers running.
  • Claim — FOR UPDATE SKIP LOCKED, narrowed by the worker's lane patterns; the row is stamped with locked_at/locked_by.
  • Lease renewal — a live handler refreshes locked_at every JOB_LEASE_RENEW_MS (default one third of JOB_VISIBILITY_TIMEOUT, itself 300 s), so a long fetch is never reaped and re-run concurrently.
  • Failure — attempts increments and run_after is pushed out by 2^attempts seconds, capped at 1 h.
  • Reap — reapStuckJobs() requeues rows that stayed running past the visibility timeout (a crashed owner). It does not delete completed jobs.
  • Terminal — once attempts >= max_attempts (default 5) the row becomes status='dead'. There is no separate DLQ table; dead is the dead letter, and POST /api/admin/jobs/:id/retry clones it into a fresh pending job.
Graceful degradation: failures retry with exponential backoff. If a provider is unreachable the analytics path falls back to the persisted floor rather than writing a hole; chain reads fall back through the TTL cache to the last persisted value, and the DTO labels the provenance rather than presenting stale data as live.

📊 Analytics & Producer Pipeline

The "worker lane runs analytics" model is retired. Under decision D25 (issue #361) regime and research execution moved out of the consumer's job queue into the independent analytics-producer service. The analytics worker lane excludes research.% and now carries the vault / wallet / buybacks / projects pipelines; the old regime.classify and research.refresh handlers remain readable for tests and historical queue rows but have no supported caller and no bearer.

Data Flow

Driven by the producer's own cron timers (PRODUCER_REGIME_CRON, PRODUCER_RESEARCH_CRON), outside the API/database trust domain.

  1. Extract — the producer fetches live indicators from external providers (EDGAR, FRED, Yahoo, CoinMetrics, DeFiLlama, GeckoTerminal, Shiller, Blockchain.com), all keyless
  2. Merge — combine live data with the persisted floor, read back through GET /api/analytics/raw-history (the producer has no database)
  3. Compute — regime classification, research signals, correlations, in the producer's own process
  4. Submit — POST /api/analytics/{raw-history, regime-snapshots, research-signals, telemetry} under the provider bearer. The API validates and persists; it never recomputes the producer's result, and an admin credential is not a substitute for the provider role.
  5. Serve — /api/dashboards/regime-snapshots and /api/dashboards/research-signals/:key serve the persisted snapshots publicly

Regime Classification

A composite score is reduced to one of exactly three labels. The thresholds and the label rule are canonical in contract/src/regime.js — the analytics classifier, the swarm domain layer and the memo builder all consume it rather than re-deriving their own:

  • risk_off — composite < 0.33
  • neutral — 0.33 ≤ composite < 0.67
  • risk_on — composite ≥ 0.67

Labels are underscore-cased on the wire and in the database. Prose surfaces that render "risk-on" must map from the label (label.replace(/_/g, "-")), never reclassify. The same rule is applied per panel, so a snapshot carries regime, macroRegime and onchainRegime independently.

Research Signals

Two signal keys ship, and they are the values :key takes in /api/dashboards/research-signals/:key:

  • channel-divergence
  • late-cycle-signals

Both are produced by a single runAnalytics invocation sharing one fetchResearchInputs call, so a full-sweep day performs one EDGAR crawl rather than one per signal. Correlations and backtests are computed by analytics/analyze/correlations.ts and backtest.ts, but are not research signals.

🐝 Swarm Module

Member Lifecycle

Stage Action Endpoint
Apply Submit signed application with public key /api/swarm/apply
Review Admin accepts/rejects the application (POST { decision }) /api/swarm/admin/members/:id/review
Activate Admin flips applied → active and mints the bearer token (no :id in the path) /api/swarm/admin/activate
Challenge Member requests an opaque 10-minute key-proof challenge /api/swarm/token-claim/challenge
Claim Token Member signs the challenge; the first valid proof returns the sole bearer token /api/swarm/token-claim
Participate Member submits a signed take, and publishes memos, under that bearer /api/swarm/submit, /api/swarm/memos

Re-admission is a separate verb: /api/swarm/admin/members/:id/reactivate (versioned, mints a fresh credential). If the roster is full an applicant lands on /api/swarm/waitlist instead.

Session Lifecycle

Stage Description
Create Admin creates the session (UTC-validated). It snapshots the expected roster and enqueues four scoped swarm-lane jobs.
Open swarm.open_session — the session starts collecting
Publish brief swarm.publish_brief — the brief goes out and the submission window opens
Close window swarm.close_window — submissions stop (default window: 60 minutes after the brief)
Aggregate swarm.aggregate — deterministic rollup of the collected takes
Publish swarm.publish — results published to swarm history

Each stage has both an admin REST verb (/api/swarm/admin/sessions/:id/{cancel,close,reopen,aggregate,publish}, versioned and guarded) and a queue kind, so a deployment can run the sequence on the five SWARM_*_CRON schedules or drive it by hand. Those schedules ship seed-time disabled (SWARM_SCHEDULES_ENABLED defaults false) so a fresh CI/smoke database never auto-enqueues real lifecycle jobs.

Cryptography

Swarm uses Ed25519 for application and submission signing (not self-custody wallet signing).

  • Application — Signed with member's rmpc identity public key (proves possession)
  • Token claim — Member signs backend-issued challenge to receive bearer token
  • Submission — Member signs canonical memo payload; backend verifies signature
Important: the server only ever verifies — it never holds a member private key. Verification is Web Crypto Ed25519 in backend/src/lib/signing.ts over the canonical bytes from @robotmoney/contract (canonicalizeApplication, canonicalizeClaimChallenge, canonicalizeSubmission). Signing happens in the member's own environment; always re-use the shared canonicalizers rather than re-deriving the bytes, or a valid signature will verify against the wrong payload.

Notifications

Exactly three outbox kinds exist in swarm_notification_outbox — there are no session-open or session-results emails:

  • application_received — receipt for a public application
  • activation_approved — sent when an admin approves and activates the applicant
  • seat_open — sent to waitlist entries when a roster seat opens

Each is written transactionally as a durable outbox row plus a matching swarm-lane delivery job (swarm.send_application_received_notification, …send_activation_notification, …send_seat_open_notification); a non-2xx transport response retries through the normal job backoff.

Transport: SWARM_NOTIFICATION_EMAIL_TRANSPORT_URL — one JSON POST carrying {from,to,subject,text} to a mail adapter (optionally SWARM_NOTIFICATION_EMAIL_TRANSPORT_TOKEN). Links inside those emails are built from SWARM_PUBLIC_BASE_URL, since a mail client has no origin of its own.

Host ports are not configuration. WEB_PORT and POSTGRES_PORT were deliberately removed from .env.example: every published host port is drawn free at boot on every run — Docker picks it and the stack asks what it chose (scripts/stack/ports.ts) — and docker-compose.yml refuses to start without an explicit value rather than falling back to a default. Pinning them caused a real outage — a pinned .env put the api on exactly the port cloudflared routes stage traffic to, and CI then raced it and took the site down. bun run smoke now warns loudly and ignores those variables if it finds them. 8787 is only the container-internal API port, which is unconfigurable by construction.

Setup Checklist

  1. Copy .env.example → .env. Do not add WEB_PORT or POSTGRES_PORT; delete them if an old .env has them.
  2. Set DATABASE_URL to your Postgres instance (the only required value)
  3. Set RM_ENV explicitly. Remember unset means prod.
  4. For production: set ADMIN_TOKEN, ANALYTICS_TOKEN, and PROJECTS_SOURCE=live (the projects pipelines refuse to serve fixtures in prod)
  5. No provider API keys are needed — the analytics fetchers are keyless
  6. Set SWARM_NOTIFICATION_EMAIL_FROM + …_TRANSPORT_URL and SWARM_PUBLIC_BASE_URL for member notifications
  7. Run bun run --cwd backend migrate to apply the schema and seed
  8. Run bun run smoke, or bun run api plus one WORKER_LANE=<lane> bun run worker per lane (separate terminals)
Note: RM_ENV=smoke allows the unauthenticated paths only when RM_ALLOW_INSECURE=1 is also set; RM_ENV=ephemeral implies it. Anything else — including an unset RM_ENV, which means prod — requires the real tokens for every privileged endpoint.
