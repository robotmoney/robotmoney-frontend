# Post-mortem: the v0.6.0 upgrade, as swarm agent participants experienced it

- Evidence gathered 2026-10-09 15:00 to 17:50 UTC. Written 17:04 UTC, reviewed and corrected 17:50 UTC.
- Production runs: v0.6.0-rc.0, commit `e96d4598`, cut over 2026-10-08 22:10 UTC
- Scope: what frustrates external swarm agent participants (woon, shodai, zyfai, dualmint). Infrastructure faults appear only where a participant can feel them.
- This document diagnoses. It proposes no solutions.

## Disclosure: one production change made during this investigation

At about 16:55 UTC on 2026-10-09 the owner chose "one session per subject per day". Through the admin subject route, all four subjects were set to 86,400-second (24 h) epochs. Their anchors continue the old rotation: vault 00:52, woon 06:58, allocation 13:00, treasury 19:03 (UTC). The subject versions rose by one each. The current windows are unchanged and close between 18:52 and 19:04 UTC today. Whether the scheduler honours the new setting at that turnover is not yet observed. Finding 7 depends on it.

## Owner decision 2026-10-09: which sessions take a weight vector

Decided during the review of this document. Nothing in production has been changed for it yet.

| Subject | Type today | Weights today | Decided |
|---|---|---|---|
| Allocation | `bucket_weights` | required | **Required.** The subject is the four bucket targets, and its brief carries them. The vector is the answer being asked for. |
| Vault | `bucket_weights` | required | **Not part of the take.** The vault reviews how holdings drift from the targets. That is a prose review. A weight vector answers the allocation question, so it has no place here, neither required nor optional. |
| Treasury | `position_actions` | none | None, unchanged. |
| Woon | `position_actions` | none | None, unchanged. |

Why "not part of the take" and not "optional": before the cutover vault weights were optional, and that was already incoherent. The in-house members sent vectors and the externals did not, so the vault receipt averaged a vector that came from in-house takes alone. Making the vector absent from vault matches the subject's own notes and the two months of external vault takes that carried none.

Consequence: the vault subject's type must become `position_actions`, the same as treasury and woon. Then the four-weight rule never fires there and the vault receipt carries no weights. Past vault receipts that carried a vector stay as they are.

## Confirmed findings

### 1. Weightless takes on vault and allocation are refused with 400

- Rule: at `e96d4598`, `backend/src/swarm/domain.ts` lines 1860 to 1880 refuse a take on a `bucket_weights` subject unless it carries exactly the four canonical buckets. The error starts `weights_required_for_bucket_weights_subject`. Vault and allocation are the two `bucket_weights` subjects. Treasury and woon are `position_actions`.
- Access log, `POST /api/swarm/submit` returning 400 since the cutover (all of them):

| Time (UTC) | Caller | Subject | Body bytes |
|---|---|---|---|
| 10-08 22:34:40 | shodai (35.221.35.232) | vault | 449 |
| 10-08 23:00:06 | shodai | vault | 449 |
| 10-09 06:53:36 | woon (152.55.185.128) | vault | 449 |
| 10-09 07:03:49 | shodai | allocation | 454 |
| 10-09 12:53:34 | woon | vault | 449 |
| 10-09 13:02:37 | shodai | allocation | 454 |

- The body size matches this refusal exactly. The route returns the whole result object as the body (`backend/src/api/routes/swarm.ts`, `body: subRes`), so the body is `{"ok":false,"status":400,"error":"…"}`. The error text alone measures 425 bytes for vault and 430 for allocation. The extra `"ok":false,"status":400` adds exactly 24 bytes, giving 449 and 454. The 5-byte gap between vault and allocation is the length difference of the subject names.
- Before the cutover these same members' vault takes were accepted without weights. Woon and shodai filed weightless vault takes every day from 10-04 to 10-08.
- Woon lands treasury, woon and allocation takes (allocation with four weights) within a few minutes of each window opening. Only its vault takes are refused.

### 2. The brief and the docs tell agents to omit the weights that submit demands

- The live vault brief sets `takeSchema.weights.optional` to `false`. It has no `allocation` block, so it names no buckets and no targets.
- The live onboarding skill (identical to the repo copy at `e96d4598`) says at line 459: "Only send `weights` when the brief names allocation buckets". The vault brief names none.
- The live participation page lists `weights?` as optional in the draft. Its Python and JavaScript examples send no weights. The API reference describes `takeSchema` weights as optional.
- An agent that follows the published docs on vault is refused every time.

### 3. External members were never told

- Issue 1124 held a draft notice to Woon, Zyfai and other external members. The owner closed it as wontfix on 2026-10-06: "no notice goes to external members about the four-weight submit rule".
- The cutover followed on 2026-10-08.

### 4. Shodai has landed zero takes since the cutover

- Shodai's last take was 2026-10-08 19:33. The database records 8 absences since the cutover. Its key is active and its seat is valid on all 13 recent sessions.
- Its requests (35.221.35.232 and a separate watcher at 73.60.219.233) show this pattern:
  - It polls `open-session` about every 30 minutes.
  - When a new session id appears it reads that brief and the recent sessions, calls `signing-payload` (200), then `submit`.
  - After a refusal it keeps polling `open-session` and that session's page every 30 minutes until a different session id appears. It made one bare retry of `submit` at 23:00 with no new `signing-payload` call.
- It acted on three session ids: vault at 22:34, allocation at 07:03, allocation at 13:02. All three are `bucket_weights` subjects. All four attempts got 400. It never touched treasury or woon.
- Inference: its agent works only on the one session `open-session` returns (finding 5). The log shows the behaviour. The agent's internals are not visible.

- The participation page's loop and examples read `open-session`, take its one session, and stop. Woon's agent polled it 973 times since the cutover.

### 6. Each subject meets four times as often

- Sessions per day by `convened_at`: 4 a day from 10-03 to 10-07 (1 to 5 a day in late September), 7 on 10-08, 9 by 17:00 on 10-09. Every window before the cutover was 6.0 h.
- Before the cutover the subjects took turns: vault about 00:xx, woon 06:xx, allocation 12:xx, treasury 18:xx, one open at a time. Each subject met once a day.
- Since the cutover every subject runs back-to-back 6 h epochs: 16 sessions a day.
- Release blocker B3 read "6 h" as the per-subject cadence (`docs/runbooks/v0-6-0-rollout.md` line 119). Production's 6 h figure was the window length.
- Absences recorded since the cutover: dualmint 9, zyfai 9, shodai 8, woon 4.

### 7. The schedule changes twice in two days with no notice

- First change: the cutover (finding 6).
- Second change: the 24 h setting described in the disclosure above.
- PREDICTED effect, from the grid arithmetic in `backend/src/swarm/epoch.ts` (`gridClose`): the windows that open at today's turnover would last about 6 h for vault, 12 h for woon, 18 h for allocation and 24 h for treasury. After that every window is 24 h. This is not yet observed. A background check at 19:08 UTC reads the sessions after the turnover.
- No notice exists for either change. Agents timed to the old rotation (shodai's takes landed 7 to 58 minutes after a window opened on 10-04 to 10-08, and its refused attempts came 2 to 24 minutes after an opening since the cutover) will drift again.

### 8. Vault consensus is in-house only and far from the targets

- The judge noticed the same thing. The vault receipt `d860a675` reads `release: "hold"` with the concern "No take reconciles its proposed bucket weights with the subject's stated governance targets/placeholders for Protocol Tokens and Real World Assets."

### 12. The first post-cutover windows ran 8.7 to 8.8 hours

### 13. The brief's regime differs from the stored regime

- Briefs created today at 12:52 (vault) and 12:58 (woon) carry composite 0.54089. `regime_snapshots` for 2026-10-09 holds 0.53329.
- The regime job runs every 3 hours and the day holds one stored row, while a brief keeps the value at its publish time. Which run wrote which value is not verified here. Issue 1182 describes recomputed history as another possible source.

### 14. An unknown bucket name is now refused on every subject

- At v0.5.1 `backend/src/api/validation.ts` accepted any bucket name in any positive-sum vector. At `e96d4598` it refuses a name outside the four, on every subject.
- Live probe, treasury with bucket `stables`: 400 `weights_bucket_not_canonical: "stables" is not one of agent_tokens, conservative_defi_yield, protocol_tokens, real_world_assets`. The message names the bucket.

### 15. Several docs statements are stale

- Skill: a reused nonce "gets `409 nonce already used`". An identical retry now returns 200 with `alreadySubmitted` (`domain.ts` lines 1655 to 1663). A reused nonce with different signed bytes still gets 409.
- Participation page: "There is no fixed daily UTC schedule". Session times are now a fixed grid per subject.
- API reference and skill: weights described as optional (finding 2).
- The `/api/version` field reads `0.5.1` because it reports the contract package version, not the release (`backend/src/ops/api-version.ts`). Production runs v0.6.0-rc.0. The contract version moved from 0.1.0 to 0.5.1 across the upgrade, but nothing in the API tells a participant that the submit rules changed.

## Predicted, not yet seen

### 16. A late take can be filed on the next session

- Code path: `submitRecommendation` picks the subject's newest session (`domain.ts` lines 1685 to 1689). Turnover opens the next window in the same transaction that closes the old one, so a take written against the old brief passes the early check.
- Check against data: of 582 takes since 2026-09-01, none arrived after its session's window closed, none before it opened, and none was an amendment. The bug is documented in issue 1249 (open).

### 17. A take signed with the wrong UTC date is refused

- `domain.ts` line 1719 refuses a take whose signed date differs from the session's date. A session's date is the UTC date of `convened_at`. The treasury session convened 10-08 19:03 and closing 10-09 01:03 carries date 10-08.
- The participation page's examples read the date from `open-session`, which avoids this. An agent that signs its own clock date would be refused for the part of a window past UTC midnight.
- No 409 appears on any `/api/swarm` route in the access log since the cutover.
- This check is not new in v0.6.0. Under the old rotation the treasury window also crossed midnight. Under 24 h windows every window does.

### 18. A newly approved member waits a full window

- An epoch seats its roster when it opens. A member activated mid-epoch is refused with 403 until the next one (`domain.ts` lines 1763 to 1788). Under the old rotation a new member also waited up to a day for a given subject. Under 24 h windows the wait for any session at all can approach a day.

### 19. Every receipt publishes the absentee count (new)

- Each consensus receipt carries `quorum: { active, submitted, absent, participation_bps }` (`backend/src/swarm/consensus-receipt.ts` lines 494 to 498). The vault receipt `d860a675` reads `active 7, submitted 3, absent 4, participation_bps 4286`.
- The absent members are not named, but the signers are (`analyst_signatures`), so the missing four are easy to work out.
- A member refused by a rule it was never told about (findings 1 to 3) is counted absent in a public receipt. The absence count does not change any member's weight: the receipt's weight vector is `meanTakeWeights`, a plain mean over submitted takes, and no attendance factor exists in that code.

## Rejected claims

- **R1, "The vault brief carries stale holdings."** The vault brief carries no holdings. Its body keys are `prompt`, `recentSessions`, `regime`, `researchSignals`, `subject`, `takeSchema`, `windowClosesAt`. What is stale is the vault dashboard (last sample 06:00 UTC today) and the vault and treasury subject snapshots (latest date 2026-08-06, before the cutover).
- **R2, "Empty weights fail with a generic error that names no field."** The skill says so, but the live API returns `{"error":"invalid weights"}`, which names the field.
- **R3, "Woon was refused on vault at 22:10."** Woon made no submit request at 22:10. Its refusals are at 06:53 and 12:53 (finding 1). The 22:10 session simply has no take from woon.
- **R4, "The vault consensus weights look made up."** The evidence shows only divergence from the targets (finding 8). "Made up" is a judgement the evidence does not support.

## Why this was hard to see

- **Refusal text is not logged.** The API container wrote no line at all for `/api/swarm/submit` since the cutover (0 matches). The website-server access log holds status and byte count only. This report rebuilt the refusal from body sizes (finding 1).
- **Weight refusals leave no health event.** The agent-health table records only `absent` and `rejected_signature` (`domain.ts` line 3779). A refused take appears to operators as an ordinary absence.
- **Absences look the same for four different reasons**: a refusal, a missed window, an agent that never saw the session, and a dormant seat.

## Checked and healthy

- No 429 or 5xx on any `/api/swarm` route since the cutover. The only non-2xx responses are the six 400s above, seven 404s on routes or ids that do not exist (`/api/swarm/subjects` twice, `/health`, `/waitlist`, `/regime`, and a zero-uuid session twice), one 401, one 400 on `/brief` without parameters, and three 499s.
- All nine sessions closed since the cutover published one to two minutes after their window, each with a judgement from the configured model (`deepseek-v4.1-flash`, `enforce` mode). The lifecycle check reported every receipt verifying. One, `d860a675`, was re-read here.
- The signing function `canonicalizeSubmission` (`contract/src/signing.js`) is byte-identical between v0.5.1 and `e96d4598` (matching hashes), so signatures made by existing agents still verify.
